# Oracle 到 PostgreSQL 数据库迁移

根据 `references/` 文件夹中记录的已知 Oracle/PostgreSQL 行为差异，揭示迁移风险并验证迁移工作。

## 何时使用

1. **规划** — 在开始存储过程、触发器、查询或 refcursor 客户端的迁移工作之前。识别哪些参考见解适用，以便提前解决风险。
2. **验证** — 迁移工作完成后，确认每个适用的见解都已得到解决，并且集成测试涵盖了新的 PostgreSQL 语义。

## 工作流程

确定任务类型：

**正在规划迁移？** 遵循风险评估工作流程。
**正在验证已完成的工作？** 遵循验证工作流程。

### 风险评估工作流程（规划）

```
风险评估：
- [ ] 步骤 1：确定迁移范围
- [ ] 步骤 2：筛选每个见解的适用性
- [ ] 步骤 3：记录风险和推荐操作
```

**步骤 1：确定迁移范围**

列出受影响的数据库对象（存储过程、触发器、查询、视图）以及调用它们的应用程序代码。

**步骤 2：筛选每个见解的适用性**

查看 [references/REFERENCE.md](references/REFERENCE.md) 中的参考索引。对于每个条目，确定迁移范围是否包含受该见解影响的模式。仅当见解可能相关时才阅读完整的参考文件。

**步骤 3：记录风险和推荐操作**

对于每个适用的见解，记录具体风险和参考文件中的推荐修复模式。标记任何需要设计决策的见解（例如，是否保留 Oracle 的空字符串作为 NULL 语义或采用 PostgreSQL 行为）。

### 验证工作流程（迁移后）

```
验证：
- [ ] 步骤 1：映射迁移工件
- [ ] 步骤 2：交叉检查适用见解
- [ ] 步骤 3：验证集成测试覆盖率
- [ ] 步骤 4：把控结果
```

**步骤 1：映射迁移工件**

识别迁移的对象并总结变更集。

**步骤 2：交叉检查适用见解**

对于 [references/REFERENCE.md](references/REFERENCE.md) 中的每个参考，确认行为或测试要求在迁移工作中得到确认和解决。

**步骤 3：验证集成测试覆盖率**

确认测试覆盖了适用见解中强调的愉快路径和失败场景（异常、排序、refcursor 消耗、并发事务、时间戳等）。

**步骤 4：把控结果**

返回一个检查清单，断言每个适用的见解都已得到解决，迁移脚本已运行，集成测试通过。
